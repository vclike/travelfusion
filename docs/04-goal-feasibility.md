# 需求澄清后的可行性分析：旅行规划

> 目标重述（原话）：近期中期以准确的航班信息，远期（如一年后）起码要有参考的价格和航班。
> 本文件回答：这个目标，现有资源够不够。

---

## 结论

| 目标 | 够不够 | 卡点 |
|---|---|---|
| **近期**（出发前 0–14 天）航班动态与延误 | ✅ **够** | **AirLabs `/schedules` 免费**给计划/预计/实际三组时间 + 出发/到达延误分钟，1,000 次/月；Aviationstack 100/月备用 |
| **中期**（1–12 个月）航班时刻、航线、班期 | ❌ **免费不可行** | 免费源窗口**仅约 10 小时**（AirLabs `/schedules` 官方原文）、Aviation Edge `/timetable` 仅 ±6h。**无任何免费源给未来班次**，需 Aviation Edge `/flightsFuture` $299/月 或 AeroDataBox Growth $99/月 |
| **远期**（1 年后）**航班时刻** | ⚠️ **边缘** | 航司只放 330–355 天，1 年时刻表多数为空 |
| **远期**（1 年后）**价格** | ❌ **不可能** | **不是额度问题，是数据不存在** |

> ⚠️ **2026-09-29 更正**：本文件初版判断「中期时刻表 ✅ 够，需小额付费」，依据是
> "AirLabs 免费档含 Live Schedules"。经 Tabbit 实测其 `/docs/schedules` 官方原文：
> *"the Schedules API returns results **up to 10 hours ahead at most**"* —— **L2 免费缺口依然存在**，
> 且免费层不存在任何提供未来班次的源。（`03-provider-matrix.md` §5 与 `07-api-reference.md` §0 已同步更正）

## 1. 为什么"1 年后的价格"这个问题本身不成立

多个来源一致：**航司在起飞前 330–355 天放票**，主流航司订票窗口约 330 天（约 11 个月）。

这意味着在**满 365 天**这个时点：

- 时刻表尚未加载 → 你查到的"航班"可能是空的或过期的
- 票价根本不存在 → 没有任何数据源能返回
- 所谓"1 年后的价格"在物理上没有被生产出来

**所以问题的正确形式不是**"查到 1 年后的价格"，而是：

> **"基于我过去观测到的这条航线价格分布，当前这个报价贵不贵？我该现在买还是等？"**

这是**历史价格基线**问题，不是实时查询问题。两者是不同产品。

## 2. 价格基线的数据从哪来

| 来源 | 内容 | 成本 | 可得性 |
|---|---|---|---|
| **自建积累** | 从启用之日起定期快照关注航线价格，逐月沉淀 | $0 | ✅ 但**必须从第一天就开始**，无法回填 |
| AeroDataBox 历史 | 180 天（Starter）/ 365 天（Growth+）航班与延误历史 | 已含在订阅 | ✅ 不含价格 |
| OAG Historical Airfare | **10+ 年历史 + 1 年前瞻**，覆盖 1500+ 订票站点 | Enterprise 报价 | ✅ 但贵 |
| TravelScrape Skyscanner Price Trends | 150K 条历史价格趋势数据集，一次性 | **$41 一次性** | ✅ 性价比最高的起步 |
| Google Flights 价格图 | 自带历史价格曲线 | 抓取/浏览器 | ⚠️ 非官方 API，且违反 ToS 风险 |
| Faredetective | 航线价格历史图（消费级） | 免费/部分付费 | 🟡 仅作交叉参考 |

**现实路径**：自建积累（$0，慢）+ TravelScrape 一次性数据集（$41，立即有历史底子）。

## 3. 达成本目标的成本估算（个人旅行规划用途）

### 方案 A：全免费

| 组件 | 方案 | 限制 |
|---|---|---|
| 国际实时 | OpenSky（4,000/日）+ Aviation Edge（30,000/月） | ADS-B 只给位置，需 flight↔icao24 映射 |
| 国际计划 | Aviation Edge Schedules API | ⏳ 时刻表前瞻天数未取证 |
| 国内 | 飞常准 MCP（14 天试用后收费） | 企业资质 |
| 远期价格 | 自建积累 | **前 3–6 个月无基线可用** |

→ 能用，但**远期目标半年内达不成**。

### 方案 B：单点付费（推荐起点）

| 组件 | 方案 | 月成本 |
|---|---|---|
| 时刻 + 历史 | **AeroDataBox Starter**（40,000 units/月、180 天前瞻时刻表、180 天历史） | **$19/月** |
| 国际实时 | Aviation Edge 免费档 | $0 |
| 国内 | 飞常准 MCP | 按企业报价 |

→ **$19/月 换到"中期 180 天的航班时刻与历史"**，对个人旅行规划够用。
40,000 units/月 对个人用途是巨量过剩（AeroDataBox Tier 1 端点仅 1 unit/次）。

### 方案 C：要把"1 年"和"价格基线"都做实

| 组件 | 方案 | 成本 |
|---|---|---|
| 365 天时刻 + 历史 | AeroDataBox **Growth**（400,000 units、365 天、扩展缓存） | $99/月 |
| 历史价格底子 | TravelScrape Skyscanner Price Trends | $41 一次性 |
| 长期价格跟踪 | 插件自建快照（吃 Growth 的额度） | 含在 $99 |

→ **$99/月 + $41 一次性**。

⚠️ AeroDataBox 条款硬约束：**任何档位（含免费）都不可转售 API 或数据**，
连"转格式/改字段名后发布"也算原始数据分发。**自用旅行规划属于 End Use，不受限**；
但只要把插件做成对外服务，就必须换数据源或采购 Scale 档（$499/月，仅 Scale 允许 B2B 衍生作品再授权）。

## 4. 这个需求把项目从"查询工具"改成了"旅行规划助手"

原设计（实时航班状态 + 多源复核）只覆盖需求的第一块。完整目标需要三层，**数据形态和刷新节奏完全不同**：

| 层 | 时间视野 | 数据 | 刷新节奏 | 主要源 |
|---|---|---|---|---|
| **L1 实时层** | 0–14 天 | 位置、延误、登机口、取消 | 分钟级 | OpenSky / Aviation Edge / 飞常准 |
| **L2 时刻层** | 1–12 个月 | 班期、航线、执飞机型、计划时刻 | 周/月级 | AeroDataBox / Aviation Edge Schedules |
| **L3 价格层** | 1–5 年 | 历史价格分布、季节性、买票时机建议 | **自建，跨月积累** | 自建快照 + 外部历史数据集 |

**L3 是新增的、也是最难的部分**，它不是"查询"，而是"观测 + 建模 + 建议"。

### 4.1 L3 的冷启动问题

价格基线**无法回填**。第 1 天启用时基线是空的，要到 3–6 个月后才有参考价值。

这意味着插件必须支持：
- **关注列表**（watchlist）：登记关心的航线/出行窗口
- **定期快照**：在额度内按节奏采样价格，落盘
- **基线计算**：按航线 × 月份 × 舱位聚合出中位数与分位数
- **时机建议**：当前报价在历史分布中的分位 → "贵/正常/便宜"

### 4.2 前面调研的两个结论在这里生效

1. **ADS-B 只给位置** → L1 必须有 flight↔icao24 映射层，否则 OpenSky 的额度再多也没法用
2. **OpenSky `/flights/*` 是夜间批处理、只有 T-1 及更早** → L1 的实时判断只能靠 `/states/*`

## 5. 我的判断

**目标本身合理，但要接受一个前提**：一年后的价格不是查出来的，是攒出来的。

如果接受这个前提，项目分三期最合理：

- **一期（L1）**：实时航班查询 + 多源复核。数据源已够，可立即开工。
- **二期（L2）**：时刻表规划。$19/月 AeroDataBox Starter 即可覆盖 180 天。
- **三期（L3）**：价格基线。**必须尽早启动**，因为它从零开始攒，早开一天早有用一天。

反过来的顺序（L3 最后做）会让基线永远追不上——这是唯一有"越晚越亏"性质的模块。
